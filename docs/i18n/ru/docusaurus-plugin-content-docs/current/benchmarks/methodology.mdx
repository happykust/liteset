# Методика тестирования

На этой странице описано, как Liteset сравнивается с upstream Apache Superset 6.0.0. Цель — **честное и воспроизводимое измерение**: одна и та же БД метаданных, те же дашборды, тот же профиль нагрузки; меняется только бэкенд.

:::caution В разработке
Числа на странице [Результаты](./results.mdx) — это демо-значения. Реальные результаты появятся в дипломном отчёте о тестировании.
:::

## Тестовый стенд

| Компонент | Конфигурация |
|---|---|
| **Железо** | TBD (одна ВМ, фиксированные CPU/RAM) |
| **ОС** | Linux (ядро 6.x) |
| **Python** | 3.12 |
| **БД метаданных** | PostgreSQL 16 + asyncpg |
| **Кэш** | Redis 7 |
| **Фронтенд** | Один и тот же SPA-бандл для обоих бэкендов |
| **Тестовые данные** | Встроенные примеры дашбордов Apache Superset |

## Тестируемое ПО

| Вариант | Стек |
|---|---|
| **Apache Superset 6.0.0** | Flask + Gunicorn (`gevent`-воркеры, `WORKERS=4`, `THREADS=10`) |
| **Liteset** | Litestar + Uvicorn + uvloop, один процесс |

Оба варианта работают с **одной и той же PostgreSQL БД метаданных**, чтобы изолировать слой данных как переменную.

## Профили нагрузки

Нагрузка генерируется через [`k6`](https://k6.io/) (приоритет) или [`wrk`](https://github.com/wg/wrk). Каждый профиль выполняется **5 минут** при фиксированном количестве virtual users (VU), после 30-секундного прогрева.

### W1 — Чтение дашборда

- `GET /api/v1/dashboard/{id}` для существующего дашборда из примеров
- 100 параллельных VU
- Запросы аутентифицированы через Flask session cookie

### W2 — Данные графика

- `POST /api/v1/chart/data` с предварительно подготовленным query context
- 50 параллельных VU
- Затрагивает и БД метаданных (read), и аналитическую БД (read)

### W3 — Запрос в SQL Lab

- `POST /api/v1/sqllab/execute/` с лёгким SELECT
- 25 параллельных VU

### W4 — Память в простое

- Без нагрузки; сервер прогревается, простаивает 60 с, фиксируется RSS

## Метрики

| Метрика | Что показывает |
|---|---|
| **RPS (req/s)** | Пропускная способность — сколько запросов в секунду обслуживает бэкенд |
| **p50 / p95 / p99 latency** | Распределение времени ответа — хвостовая задержка отражает очереди |
| **Resident memory (МБ)** | Установившийся объём RAM — критично для стоимости / плотности |
| **Сustained concurrency** | Максимум одновременных подключений без деградации latency |
| **Error rate** | Доля не-2xx ответов; должна оставаться 0 |

## Сопоставимость

Оба бэкенда разворачиваются:

- **За одинаковым reverse proxy** (или вообще без proxy) — сетевая часть одинакова
- **С одинаковой политикой кэширования** — оба используют Redis с одинаковыми TTL
- **На одних и тех же фикстурах** датасетов / дашбордов — bootstrap из снапшота
- **С одинаковым auth-путём** — Flask-подписанная session cookie выпускается один раз и переиспользуется

## Воспроизводимость

Скрипты нагрузки, манифесты инфраструктуры и сырые результаты хранятся в директории [`liteset/benchmarks`](https://github.com/happykust/liteset) репозитория. Каждый результат на странице [Результаты](./results.mdx) ссылается на свой запуск.
